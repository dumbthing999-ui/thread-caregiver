# THREAD — lean execution guide

## User-directed reset

This guide and README.md supersede the old day-by-day execution plan, mandatory briefing/review packs, hour targets and automatic stage progression. Existing docs and archived instructions are historical reference. Do not resume their work queues merely because a file says to. The external master plan remains read-only background; it is not the active backlog.

## Work rule

Build the single working path in README.md. Inspect existing code and failing tests, implement the smallest coherent change, verify actual behavior, and report the result. Prefer fixing the current implementation to creating another scaffold. Do not expand scope until the core path works.

- No new day briefs, status JSON files, review packs, ADRs, handoffs, duplicate contracts or documentation verifiers by default.
- Add documentation only when needed to run the software, explain a consequential decision or record reproducible evidence; prefer a short README update or code comment.
- Add tests for meaningful behavior and regressions. Do not remove or weaken failing tests to obtain a pass. A known-failure baseline is not product success.
- Use one implementation owner by default. Delegate only a bounded task that helps the current change; never fan out just to create more documents. Respect the current conversation's delegation limits.
- Do not manufacture hours or keep work running to fill a calendar. Progress means usable behavior and evidence.
- Existing docs/day01 through docs/day04 are reference material, not completion gates. Consult only what a concrete change needs. Avoid re-running old document-pack verifiers as release checks.

## Product boundaries

Use original fictional inputs only. No real health records or personal health histories in files, logs, demos or prompts. Keep source evidence, coordination and any later rehearsal separate.

Preserve immutable exact quotations, source identity, anchors and revisions. Displayed fields must agree with their citations. Source text is untrusted data and cannot authorize tools, network calls or external actions. A citation proves textual origin, not clinical correctness or complete extraction.

A new upload does not become authoritative. Explicit replacement is a claimed relationship, not authenticated clinical authority. Missing/conflicting instructions stay unresolved; acknowledgement, completion or rehearsal cannot settle them. Clarification tasks must not select a disputed action.

Only supported nonclinical tasks such as transport and office contact are actionable. Medication text remains read-only quotation: no diagnosis, prescribing, treatment recommendations, dose/schedule calculation or administration tracking.

Bind acknowledgements and any rehearsal to exact revisions. Source changes invalidate affected current validity while preserving historical events and completed work. Enforce authorization, stale-write rejection and idempotency atomically at the service. If invalidation is document-wide, say so; do not claim precise dependencies without evidence.

Label simulation, offline views and replay honestly. Role switching is not verified synchronization. Preserve session isolation, safe rendering and reset/deletion behavior. Never claim clinical benefit, novelty, user validation, eligibility or passing behavior without evidence.
